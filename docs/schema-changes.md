# Schema changes (manual migrations)

Apply in order on PostgreSQL. The repo has no Alembic tree; align the database with [`backend/models.py`](../backend/models.py) after running these statements.

**Single-file script:** For a consolidated script (enums, `core.materials`, `wms.shades`, `wms.fabric_rolls`, receipts split columns, `receipt_items` FKs), see [`sql/wms_cpc_schema_build.sql`](sql/wms_cpc_schema_build.sql).

**Prerequisites:** Schemas `core` and `wms` exist; existing enum types `wms.warehouse_type`, `wms.receipt_type`, `wms.receipt_status`, `wms.transaction_type` exist.

---

## 1. `core.materials` (if not already present)

On **CPC_INTEGRATED_SYSTEM**, `core.materials` already exists with PK **`material_id`** and **`material_name`** — do not create this table from the WMS repo. WMS only references it via FK.

**Rollback:** `DROP TABLE IF EXISTS core.materials CASCADE;` (only if no dependents).

---

## 2. `wms.shades`

```sql
CREATE TABLE wms.shades (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    client_id INTEGER NOT NULL REFERENCES core.clients(client_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    color_id INTEGER NOT NULL REFERENCES core.colors(color_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    shade_number INTEGER NOT NULL,
    CONSTRAINT uq_wms_shades_client_color_number UNIQUE (client_id, color_id, shade_number),
    CONSTRAINT ck_wms_shades_positive_number CHECK (shade_number > 0)
);

CREATE INDEX IF NOT EXISTS ix_wms_shades_client_color ON wms.shades (client_id, color_id);
```

**Rollback:** `DROP TABLE IF EXISTS wms.shades;`

## 3. `wms.fabric_rolls`

Create when no legacy `dyed_fabric_rolls` rename is needed:

```sql
CREATE TABLE wms.fabric_rolls (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    roll_id VARCHAR(50) NOT NULL UNIQUE,
    barcode VARCHAR(100) UNIQUE,
    client_id INTEGER NOT NULL REFERENCES core.clients(client_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    color_id INTEGER REFERENCES core.colors(color_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    material_id INTEGER NOT NULL REFERENCES core.materials(material_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    lot_number VARCHAR(50),
    gsm NUMERIC(6,2),
    fabric_width NUMERIC(6,2),
    weight_kg NUMERIC(8,3) NOT NULL,
    meterage NUMERIC(8,2),
    status VARCHAR(3) NOT NULL DEFAULT 'in',
    rack_id INTEGER REFERENCES wms.warehouse_racks(id) ON UPDATE CASCADE ON DELETE SET NULL,
    defect_points INTEGER DEFAULT 0,
    quality_grade VARCHAR(20),
    shade_id INTEGER REFERENCES wms.shades(id) ON UPDATE CASCADE ON DELETE SET NULL,
    received_date TIMESTAMP,
    issued_date TIMESTAMP,
    supplier VARCHAR(100),
    remarks TEXT,
    CONSTRAINT ck_fabric_rolls_status CHECK (status IN ('in', 'out'))
);
```

If migrating from `wms.dyed_fabric_rolls`, use `ALTER TABLE ... RENAME TO fabric_rolls`, add/rename columns to FKs, backfill `client_id`/`color_id`/`material_id`/`shade_id`, then drop obsolete VARCHAR columns.

**Rollback:** `DROP TABLE IF EXISTS wms.fabric_rolls;`

## 4. `wms.receipts` — split source/target locations

**Before altering**, inspect ambiguous legacy IDs if upgrading from `source_location_id` / `target_location_id`:

```sql
-- Example orphan check (adjust after you classify legacy rows)
SELECT id, source_location_id FROM wms.receipts WHERE source_location_id IS NOT NULL;
```

Add new columns and backfill (application-specific), then enforce checks and drop old columns:

```sql
ALTER TABLE wms.receipts
  ADD COLUMN IF NOT EXISTS source_warehouse_id INTEGER REFERENCES wms.warehouses(id) ON UPDATE CASCADE ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS source_logical_location_id INTEGER REFERENCES wms.logical_locations(id) ON UPDATE CASCADE ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS target_warehouse_id INTEGER REFERENCES wms.warehouses(id) ON UPDATE CASCADE ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS target_logical_location_id INTEGER REFERENCES wms.logical_locations(id) ON UPDATE CASCADE ON DELETE SET NULL;

-- Backfill from legacy columns only after mapping each id to warehouse vs logical_location:
-- UPDATE wms.receipts SET source_warehouse_id = ... WHERE ...;

ALTER TABLE wms.receipts
  ADD CONSTRAINT ck_receipts_source_one_location_type
    CHECK (NOT (source_warehouse_id IS NOT NULL AND source_logical_location_id IS NOT NULL)),
  ADD CONSTRAINT ck_receipts_target_one_location_type
    CHECK (NOT (target_warehouse_id IS NOT NULL AND target_logical_location_id IS NOT NULL));

-- After backfill:
-- ALTER TABLE wms.receipts DROP COLUMN source_location_id, DROP COLUMN target_location_id;
```

**Rollback:** Drop the new columns and constraints; restore legacy columns from backup if required.

## 5. `wms.receipt_items` — FKs to `fabric_rolls` and `boxes`

```sql
-- Widen roll_id to BIGINT to match fabric_rolls.id
ALTER TABLE wms.receipt_items
  ALTER COLUMN roll_id TYPE BIGINT USING roll_id::bigint;

ALTER TABLE wms.receipt_items
  ADD CONSTRAINT fk_receipt_items_roll
    FOREIGN KEY (roll_id) REFERENCES wms.fabric_rolls(id) ON UPDATE CASCADE ON DELETE SET NULL;

ALTER TABLE wms.receipt_items
  ADD CONSTRAINT fk_receipt_items_box
    FOREIGN KEY (box_id) REFERENCES wms.boxes(id) ON UPDATE CASCADE ON DELETE SET NULL;
```

Use `NOT VALID` then `VALIDATE CONSTRAINT` on large tables if needed.

**Rollback:** `ALTER TABLE wms.receipt_items DROP CONSTRAINT IF EXISTS fk_receipt_items_roll;` (and box); restore column types from backup if necessary.

## 6. `wms.dyed_fabric_rolls` / `wms.undyed_fabric_rolls` — ingestor + roll lineage

```sql
ALTER TABLE wms.dyed_fabric_rolls
  ADD COLUMN IF NOT EXISTS ingested_by INTEGER REFERENCES core.users(id),
  ADD COLUMN IF NOT EXISTS original_roll_id BIGINT REFERENCES wms.dyed_fabric_rolls(id);

ALTER TABLE wms.undyed_fabric_rolls
  ADD COLUMN IF NOT EXISTS ingested_by INTEGER REFERENCES core.users(id);
```

`ingested_by` is set server-side from the authenticated user on `POST /dyed-fabric-rolls` and `POST /undyed-fabric-rolls` — never client-supplied. `original_roll_id` (dyed rolls only) self-references another dyed roll for lineage (e.g. a roll split/re-ingested from an existing one); the column and API support it, but no ingestion UI sets it yet.

**Rollback:**
```sql
ALTER TABLE wms.dyed_fabric_rolls DROP COLUMN IF EXISTS ingested_by, DROP COLUMN IF EXISTS original_roll_id;
ALTER TABLE wms.undyed_fabric_rolls DROP COLUMN IF EXISTS ingested_by;
```

## `wms.receipt_type`: `cutting` → `internal`

New databases should use `internal` (see [`backend/startup/bootstrap.py`](../backend/startup/bootstrap.py)). If an older database still has enum label `cutting` and rows using it:

```sql
ALTER TYPE wms.receipt_type ADD VALUE 'internal';

UPDATE wms.receipts
SET receipt_type = 'internal'::wms.receipt_type
WHERE receipt_type::text = 'cutting';
```

If `'internal'` is already present, skip the `ALTER TYPE` line (PostgreSQL will error on duplicate).

Removing the old `cutting` label from the PostgreSQL enum requires recasting columns and dropping/recreating the type; only do that after no rows reference `cutting`.

## Notes

- **Shade sequence:** Allocate `shade_number` per `(client_id, color_id)` in the application (`MAX(shade_number)+1` in a transaction) or via a trigger.
- **Receipt locations:** Each of source and target allows at most one of warehouse vs logical location; both may be null.
